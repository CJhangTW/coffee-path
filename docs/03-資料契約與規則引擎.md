# 03｜資料契約、關卡規則與配方引擎

本章是開發交付中的 **data contract**。請先用資料驅動教學，不要把每一關寫成不可重用的獨立邏輯。

## 1. 資料分類與名詞定義

| `kind` | 語義 | 例子 | 能否作為「獨立飲品」統計 |
|---|---|---|---|
| `drink` | 被獨立識別的常見飲品類型 | Cortado、Latte | 依去重規則判斷 |
| `alias` | 地域名或其他語言別名 | Bica 指向 Espresso 家族 | 不另計 |
| `preparation` | 萃取方法 | Pour-over、Cold Brew | 不直接與 drink 加總 |
| `technique` | 沖煮技法 | Turbo Shot、4:6 | 不另計 |
| `equipment` | 器具或產品構造 | V60、Chemex | 不另計 |
| `experimental` | 新興、創作或實驗性做法 | Milk Brew 等 | 記錄但不當傳統確立款 |

原料政策：`strict`（只用三種原料及其物理狀態）、`derived`（牛奶分離乳脂等衍生材料）、`adapted`（傳統有糖但改成無糖等）、`excluded`（需要第四種原料，僅知識對照）。初版以 strict、少量 derived 為主。

每筆知識須有 `sources`（可為空但必須 `provisional`，且應列待查）、`confidence`（`reviewed`／`provisional`／`experimental`）、`updatedAt`。不要用單一官方比例宣稱所有店家一致。`name.zhHant`、`name.en` 均須非空字串。

## 2. 飲品卡結構（`drinks.core.json`）

參見 `samples/drinks.core.json`；實作應寫 `validateDrink()`，不接受空 ID、重複 ID、未知相關 ID、壞掉的 source ref 或違規 `kind`。若資料屬 `experimental`，必須附上「並非全球公認獨立飲品」說明。

建議欄位：

```json
{
  "id": "cortado",
  "kind": "drink",
  "family": "espresso-milk",
  "name": { "zhHant": "可塔朵", "en": "Cortado" },
  "aliases": [],
  "ingredientPolicy": "strict",
  "baseMethods": ["espresso"],
  "temperatures": ["hot"],
  "intro": "用約等量熱牛奶柔化濃縮咖啡。",
  "explain": "比拿鐵的牛奶少，通常用小杯呈現。",
  "deep": "比例依國家與咖啡店有所差異；不可把 1:1 當作唯一配方。",
  "ranges": { "espressoG": [25, 45], "milkG": [25, 55] },
  "relatedDrinkIds": ["espresso", "flat-white"],
  "sources": ["src-example-coffee-01"],
  "confidence": "provisional",
  "updatedAt": "2026-11-14"
}
```

`ranges` 只給相近比較演算法作參考；不代表正式命名的硬性門檻。首版資料可保留 `provisional`，但顯示時要明示未完整查證；正式發布至少核心章節升級為 reviewed。

## 3. 課程關卡結構（`lessons.json`）

採 JSON 定義「內容及參數」，不在 JSON 寫程式、任意 HTML 或 JS 條件字串；用事先實作的 `challenge.type` 對應純函式判定。

```json
{
  "id": "water-02",
  "chapterId": "water",
  "order": 2,
  "title": "加水之後，是不是另一杯咖啡？",
  "learningObjective": "能區分萃取後加水與延長萃取。",
  "prerequisites": ["water-01"],
  "scene": "cup-water-addition",
  "prompt": "試著幫 Espresso 加 100 g 熱水。",
  "initialRecipe": {
    "methodId": "espresso", "doseG": 18, "yieldG": 36,
    "addedWaterG": 0, "milkG": 0, "temperature": "hot",
    "foam": "none", "mixing": "mixed"
  },
  "allowedControls": ["addedWaterG"],
  "challenge": {
    "type": "parameter-and-choice",
    "parameter": "addedWaterG", "minimum": 80,
    "question": "Americano 與 Lungo 的主要區別是？",
    "options": [
      {"id": "after", "text": "美式是萃取後再加水"},
      {"id": "same", "text": "只差杯子大小"}
    ],
    "correctOptionIds": ["after"]
  },
  "rewardDrinkIds": ["americano"],
  "summary": {
    "intuitive": "美式咖啡是先萃出 Espresso，再加熱水。",
    "explain": "水沒再通過咖啡粉，所以與拉長萃取的 Lungo 不同。",
    "deep": "配方和出杯量並非統一，這是關鍵製程差異。"
  },
  "sourceIds": ["src-example-coffee-01"]
}
```

`prerequisites` 是旅程建議順序；從圖鑑或老手入口可直接檢視任一關，**但不自動通關、不自動給 BP**。

## 4. 關卡引擎狀態機

```text
locked (旅程順序限制，可由老手模式檢視)
  → ready → briefing → interacting → checking
                     └── checking (wrong → feedback → interacting)
                                     └── correct → completed
                                                    → reward granted once
                                                    → next / revisit
```

- `startLesson(id, progress)`：不修改持久化資料，回傳課程初始狀態。
- `applyInteraction(state, action)`：驗證允許控制與數值範圍，更新場景參數。
- `evaluateChallenge(lesson, recipe, answer)`：回傳 `{passed,reasonCode,feedbackKey}`；不得產生隨機結果。
- `completeLesson(progress,lessonId)`：純函式，回傳新 progress、獲獎事件、首次完成旗標；再次執行不加分。
- UI 負責 DOM，domain engine 不依賴 UI 或 Storage。

## 5. 豆點的決定性計算

- `lessonCompleted`: 每個唯一 lessonId +10 BP。
- `chapterCompleted`: 每個完整章節 +20 BP，一次性。
- `finalBonus`: 首次通過 `final-01` +30 BP，一次性。
- `totalBP` 以 `completedLessonIds` 與 `awardedAchievementIds` 重新計算；若儲存快取的 BP 與計算不同，以可驗證事件為準。
- 不採負點數、扣點、每日獎勵或重複刷分。
- 圖鑑解鎖依 `rewardDrinkIds` 去重，若同一飲品在多關重複出現只收藏一張。
- 進階層解鎖：實際旅程進度可解鎖；`expertBypass=true` 或 `unlockAllKnowledge=true` 則直接開啟所有教學層，**不修改 BP**。

## 6. LocalStorage 資料契約

Storage key：`coffeepath.progress.v1`。此為全新 CoffeePath 規格的唯一寫入 key。若在**同一個 origin** 存在早期測試資料（舊 key `coffeelearn.progress.v1`），則在新 key 不存在時可讀取舊 key、驗證格式後單次遷移，不得覆蓋新資料或每次雙寫。**不同子網域的 localStorage 相互隔離**：從 `cafelearn.cjhang.com` 移至 `coffeepath.cjhang.com` 時，新站不能直接讀取舊站進度；需要由舊站提供匯出、由新站手動匯入，或明確告知無法自動移轉。尚無正式上線站時，可只提供 migration 測試。

```json
{
  "schemaVersion": 1,
  "completedLessonIds": ["intro-01", "water-01"],
  "awardedAchievementIds": ["chapter-intro"],
  "collectedDrinkIds": ["espresso"],
  "preferences": {
    "expertBypass": false,
    "unlockAllKnowledge": false,
    "visualMode": "auto",
    "reducedMotion": false
  },
  "lastRoute": "#/journey/water-02"
}
```

- `localStorage` 可能停用、遭到清除、無痕模式結束即消失。儲存失敗時繼續提供匿名、暫存狀態並顯示友善訊息。
- 不存個人資料，不傳伺服器，不把 BP 作安全身份。使用者可以編輯 DevTools/localStorage，這不是資安漏洞。
- V1.1 建議加入匯出／匯入 JSON：僅小於 1 MiB 的檔案；驗證 schemaVersion、白名單 ID、字串長度與類型；無法解析時不得覆寫既有進度。
- 舊版本需明確 migration；不可任意重設或損毀既有進度。
- 沒有跨裝置同步，不應聲稱能保留永久紀錄。

## 7. 實驗室 Recipe 資料結構

### 7.0 萃取與加水的視覺階段

- `extractionFrame(progress)` 將 0–1 的示意進度轉換為水流、咖啡液流與杯中液量：先有水通過粉床，再有咖啡液入杯，完成後水流停止。此為教學時序，不預測萃取率或真實流速。
- `pourFrame(from,to,progress)` 將追加水量從起點轉至目標；只有增加水量才顯示倒入。減少水量或重設表示調整配方，直接切至新值，不暗示水倒流。
- `pourTransition(current,previousTarget,nextTarget)` 依前一次目標判斷增加或減少；即使上一段動畫尚未走完，降低目標仍立刻切換，不誤判成繼續倒水。
- 2D、3D 與減少動態模式需保持相同的因果順序與文字摘要；減少動態時可直接呈現最終狀態與流程文字。切換顯示模式應保留配方，不重播已完成操作。

```json
{
  "methodId": "espresso",
  "doseG": 18,
  "yieldG": 36,
  "addedWaterG": 120,
  "milkG": 0,
  "temperature": "hot",
  "foam": "none",
  "mixing": "mixed"
}
```

- **單位統一採重量 g**。在介面需明確標示重量；不可未換算就把 mL 直接當 g。
- `doseG` 是乾咖啡粉量；`yieldG` 是咖啡液重量；`addedWaterG` 是萃取後加水；`milkG` 是額外加入牛奶。
- 不同基底以 `methodId` + 專屬 `brewParams` 呈現；非 espresso 不得偽裝成 9 bar 的義式模型。
- 粉量及出杯量採可行的教學上下限，超出界限顯示原因或禁用；`NaN`、負數、非數字、極大值一律驗證。
- 乳質若為 `none` 必須 `milkG=0`；有奶時 `foam` 可為 liquid/microfoam/thickfoam，兩者含義一致。
- `mixing` 不可偷偷代表萃取溫度；例如 `espresso-over-cold-milk` 必須滿足 espresso 基底且冷牛奶情境。

## 8. 風格判斷引擎：先解釋再分類

> **禁止**用單一閾值 `if milkG > 150 then Latte else Flat White` 產生唯一標準名稱。

### 8.1 純函式 API

```js
normalizeRecipe(input)     // 驗證＋正規化，回傳狀態與錯誤
computeComponents(recipe)  // 回傳各部分重量與可視化組成
matchStyles(recipe,catalog) // 回傳 0–3 個可能的相近款式、匹配原因
explainChange(before,after) // 說明使用者剛改變的物理／流程因素
compareRecipes(a,b)        // 列出哪個變數不同及其影響
```

`matchStyles` 回傳示例：

```json
{
  "primaryFamily": "espresso-milk",
  "matches": [
    { "drinkId": "flat-white", "matchLevel": "close", "reasons": ["相近杯量", "細緻奶泡"] },
    { "drinkId": "latte", "matchLevel": "possible", "reasons": ["同為牛奶與 Espresso 的組合"] }
  ],
  "disclaimer": "咖啡名稱受地方與店家定義影響，此為相近風格而非唯一正解。"
}
```

### 8.2 初版判斷策略

1. 先檢查方法、三原料限制、是否有奶、是否加水、溫度和製作順序等必要條件。
2. 在符合的家族內比較配方與示例區間；區間交疊時提供多個結果，避免過度自信。
3. 用 `matchLevel: close | possible | related` 表達接近程度，**不要顯示未經校驗的精確 94.8% 機率**。
4. 每個結果必須提供說明原因，且來源由靜態資料支援。
5. 對不符合現有風格的合法配方，顯示「自訂咖啡／尚無常見對應名稱」，不可任意創造官方名稱。
6. `Dirty` 必須具備冷奶和熱 Espresso 先後形成的分層情境，不只是冰拿鐵。
7. `Lungo` 與 `Americano` 的區別是**萃取水是否持續通過粉餅**，不是水量相同就可互換。
8. Cold Brew 的萃取溫度和冰飲的**飲用溫度**是不同維度，不可混用。

### 8.3 不能做的「假科學」

- 不用 `espressoG / cupG` 當成真實 TDS；實際濃度要靠量測或合理成分模型。
- 不把顏色直接當作萃取率；圖像只做層次示意。
- 不把咖啡因含量和濃縮程度畫上等號；缺少豆種、出杯量及實測條件。
- 不把 Flat White、Cappuccino 設成全球統一硬門檻。

## 9. 範例分類檢驗

| 輸入 | 結果必須包含 | 不可發生 |
|---|---|---|
| Espresso 36g + 120g 熱水、無奶 | Americano 類 | 誤判成 Lungo |
| Espresso 粉 18g、直接萃出 72g、無追加水 | Lungo 類 | 誤判成 Americano |
| Espresso 36g + 120g 熱奶與 microfoam | Flat White、Latte 可能重疊，需說明 | 宣稱唯一官方名稱 |
| Espresso 36g + 240g 熱奶與 microfoam | Latte 類 | 誤稱 Cortado |
| Espresso 36g → 冷奶 100g 上方，不攪拌 | Dirty 風格 | 誤稱為一般攪拌冰拿鐵 |
| Cold Brew 180g + 牛奶 100g | Cold Brew Latte 類 | 誤認基底為 Espresso |
| 直接浸泡冷水取得咖啡、隨後加冰 | Cold Brew 類 | 誤判 Flash Brew |
| 沒有符合的資料 | 自訂配方 | 虛構新的通行咖啡名稱 |

## 10. JSON 資料規範

- 格式使用 UTF-8；無註解；key 採 camelCase、ID 採 kebab-case。
- 所有關聯 ID 必須在 `drinks.*.json` 或 `methods.json` 可找到；不可有循環章節 `prerequisites`。
- 外部來源可以存於 `sources.json` 供使用者自行點開，**頁面載入時不需向外部來源發 request**。
- 靜態 JSON 不含使用者進度；只讀入產品知識與教學設定。
- 內容審稿時明確註記 `reviewed`、`provisional`、`experimental`，並保留最後查核日期。
