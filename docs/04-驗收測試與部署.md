# 04｜驗收、效能、無障礙、內容品質與部署

## 1. Definition of Done（所有階段共同門檻）

- 功能有清楚操作入口、可回到上一個狀態、可錯誤復原；手機與桌機正常。
- 未開啟 WebGL／Three.js 加載失敗時，課程與實驗室仍完整可用。
- 程式未呼叫遠端 AI、API、資料庫、Cloudflare Workers／Pages Functions。
- 所有核心畫面不依賴圖片、影片、外部字型或 3D 模型。
- 同源 JSON／JS 模組皆能在 Python 靜態伺服器正常載入；不得只能在 `file://` 下執行。
- `domain/*` 純函式、可原生 browser test；新增資料檔可通過 ID 與來源完整性檢驗。
- 所有主要控制提供可見 label、鍵盤操作與可閱讀的文字解說。
- 有 README（架站、部署、資料新增、測試）及授權資訊；新增功能有相應單元或手動驗收案例。

## 2. M1 核心循環（先完成才可做 3D）

### M1 必須驗收

1. 使用者打開首頁可選擇「開始旅程」與「直接探索」。
2. Journey 完成 `intro-01`、`water-01`、`water-02`，能透過控制調整水量，並選答核心差異。
3. 首次通關 BP 正確增加，重玩不增加；關閉頁面後重新開啟可讀取進度。
4. 可以看到已收集的 Espresso 與 Americano 卡片。
5. `water-02` 的學習重點確實是「萃取後加水」，不是純粹水變多。
6. localStorage 故障時網站仍可完成一個關卡，並告知進度只能暫存。
7. 2D 杯型與文字摘要可以完整說明咖啡與加水構成。

## 3. 完整 Journey 驗收

- 18 個關卡 IDs 與 `prerequisites` 沒有循環；所有章節都可由進度頁找到。
- 每關至少有一次必要操作和一題理解檢查；答錯可重試，不扣分。
- 結業後有具體的知識回顧，而不是只有恭喜畫面。
- `chapterCompleted` 僅首次給獎；`final-01` 額外獎勵僅一次。
- 熟手入口直達 Lab、Atlas、深入說明，但不改寫通關與豆點紀錄。
- 隨時返回旅程，仍保有既有通關狀態。
- 直接開啟 `#/journey/milk-03` 等深連結，能合理處理未過關狀況，而非空白頁。

## 4. Lab 配方判斷案例（自動化＋人工驗收）

| Case | 操作 | 正確結果 |

## 5. 效能驗收目標（待實機驗證，非目前測得值）

- 以普通中階 Android Chrome 與 iOS Safari 做至少一輪實測；桌機 Chromium、Firefox、Safari 主要功能測試。
- 以 4G 行動網路／中階裝置測：首頁最大內容繪製 LCP ≤ 2.5 秒、操作反應 INP ≤ 200 毫秒、版面位移 CLS ≤ 0.1 為方向性目標；實際結果受裝置與網路影響。
- 首頁絕不可預先載入 Three.js；使用者進入支援 3D 的頁面後才載入；初始互動 JS 自有程式碼盡量控制在低百 KB 級，不為美觀大量載入套件。
- 3D 手機理想可見時維持 30 FPS；達不到或 WebGL 崩潰時立即切換 2D，且保留互動與畫面內容。
- 限制 canvas 像素數、DPR、draw calls；切換頁面／背景化時停止無用 render loop。
- 對 `prefers-reduced-motion` 減少／停止裝飾性動畫；測試能否透過設定切換 2D。
- 慢速網路下可先看文字，不能讓整頁阻塞於 3D 或延伸圖鑑載入。

## 6. 無障礙與 RWD

- 參考 WCAG 2.2 AA：鍵盤可操作、明顯焦點、色彩對比、可見標籤、不同狀態不只用顏色區分。
- 手機最窄 320 CSS px 能完成主要流程，不水平溢出。
- 互動主目標建議 ≥ 44×44 CSS px（優於 WCAG 2.2 AA 部分最低要求）。
- SVG/Canvas 必須有語意文字或 HTML 說明；3D 不得包含唯一可讀的資訊。
- 資料量增長後，圖鑑需分批展示；不要求在畫面同時渲染所有節點。

## 7. 資料正確性驗收

- 所有資料 `id` 唯一，relatedIds 與 sourceIds 可解析，沒有孤兒引用。
- 核心課程不得引用 `excluded` 飲品當作三原料範例。
- 每個需要定量描述的內容註明「示例」、「常見」、「地區差異」或具體研究來源。
- 不把 V60／Chemex 直接當作飲品數量；不把 Bica／Espresso 等別名重複算成兩種獨立款式。
- 不可用沒有來源的硬閾值宣稱 Flat White、Latte、Cappuccino 的全球唯一分界。
- 原料判定須含水的物理狀態冰、牛奶奶泡；其他食品原料不合規。
- 公開開源前，逐項審核核心資料卡及參考文獻，更新 `confidence`。

## 8. Cloudflare Pages + GitHub 部署操作

1. 在 GitHub 帳號或組織下建立公開 `coffee-path` Repository（全小寫、連字號、無版本號），提交 `site/` 與 docs，但不得有 API 金鑰、密碼及個資。
2. Cloudflare Workers & Pages 建立 Pages 專案，**建議 Project name = `coffee-path`**，以 Git integration 連結同名 GitHub 儲存庫。`coffee-path.pages.dev` 實際名稱可能已被占用，請依 Cloudflare 當時可用性選擇，這不影響 `coffeepath.cjhang.com`。
3. 選擇無框架（None）；Build command 設定 `exit 0`；Build output directory 設成 **`site`**（不是根目錄 `.`）。
4. 部署成功會產生 `<project>.pages.dev`；先測試首頁、直接開 hash 深連結與資料載入。
5. Pages 專案 > Custom domains > Set up a domain，加入 **`coffeepath.cjhang.com`**（注意此網址沒有 `coffee-path` 的連字號）。
6. 如果 `cjhang.com` DNS 由同個 Cloudflare Zone 管理，通常可以依頁面流程建立 CNAME；若在外部 DNS 管理，照官方指示建立指向 `<project>.pages.dev` 的 CNAME。**不能只建立 DNS CNAME 而跳過 Pages 的自訂網域設定。**
7. 測試 HTTPS、DNS 生效、行動裝置、快取更新與回上一頁；正式環境不設 Functions／Workers。
8. 如果日後要加快取策略、Service Worker 或外部資產，須先進行安全及相容性設計，不能以核心功能必要條件加入。
9. 驗證頁籤標題是 `CoffeePath`、GitHub README 主標題是 `CoffeePath`、Repository slug 為 `coffee-path`；meta description、canonical、og:title、logo 的文字識別保持一致，避免在 console、URL 或頁面留下舊品牌文字。

截至 2026-11-14：Cloudflare Pages 靜態資產請求不觸發 Functions 時免費且不限次數；免費方案官方文件列 500 次/月建置、20,000 個檔案/站、單檔 25 MiB 上限，後續以官方當時政策為準。

## 9. 使用者測試（無追蹤後端）

- 找至少 5 位初學者、3 位熟手，觀察是否能不用提示完成序章；在 5 分鐘時可否自己解釋差異。
- 記錄是否誤解：① Americano vs Lungo，② Cold Brew vs Flash Brew，③ Dirty vs Iced Latte，④ Flat White vs Latte 是有重疊的命名風格。
- 第一輪產品假設：至少 4/5 新手能說對兩組主要差異；不足就修改教材，不先追加動畫。
- 訪談及觀察可人工記錄，網站不用安裝 Google Analytics 或其他追蹤 SDK。

## 10. 品牌與網址驗收

- GitHub 名稱 `coffee-path`，網站品牌 `CoffeePath`，自訂網域 `coffeepath.cjhang.com`，Pages 專案建議 `coffee-path`。
- `README`、`AGENTS.md`、網站 `<title>`、頁首品牌、頁尾、教學卡片抬頭、分享文案、測試描述與 GitHub About 不得留錯字／舊品牌。
- 不在 JSON 內容的飲品別名欄位夾帶產品名；品牌由 site config 控制。
- 測試 `localhost`、`*.pages.dev` 預覽、正式自訂網域三種 host，路由／靜態資源不能硬編碼 production origin。
- 若曾以舊 key 儲存學習進度，僅**同一個 origin** 能讀取並遷移；跨子網域無法直接存取 localStorage，若舊站曾對外使用，需規劃 JSON 匯出／匯入，而非宣稱自動遷移。
- 尚未執行 GitHub 建庫、Cloudflare 專案建立、DNS 修改或正式部署；此處僅為將來執行標準。
